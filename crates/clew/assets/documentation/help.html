CODECLEW DOCUMENTATION

Understand your system, with source you can inspect

Codeclew docs maintains a local documentation repository alongside your service repositories. It captures committed source, gives an agent bounded evidence for an explanation, and publishes an offline reader. Each explanation retains its source references and a record of what it depends on.

Install and start

Prebuilt packages support macOS ARM64 and x86-64, and Linux x86-64. On Windows use WSL2. The launcher needs Git and Python 3.11 or newer. Source-syntax documentation does not need the service to build. Compiler providers additionally need the admitted project toolchain and dependencies; Kotlin workers use JDK 21.

curl -fsSL https://codeclew.github.io/codeclew/install.sh | sh
clew --version
clew skill install --agent codex
clew docs init --root ./architecture --title "System architecture"

The installer prints the launcher location; add it to PATH if necessary. For another supported agent, inspect clew skill install --help. Update with clew upgrade. Review any customized skill before replacing it with --force. For offline installation, use the installer, archive and matching checksum files from the same GitHub release.

Open architecture/docs/help.html or architecture/docs/runbooks.html immediately. After publication, open architecture/docs/index.html. The pages work offline; an optional local server is convenient:

cd architecture
python3 -m http.server 8767 --bind 127.0.0.1

How documentation is produced

  1. Register: choose a service, committed revision, source roots and optional contract files; bind its local checkout.
  2. Capture: clew docs check builds the selected evidence and reports changes or gaps.
  3. Explain: an agent reads bounded work, writes prose and diagram steps tied to evidence, and submits a proposal.
  4. Publish: deterministic checks validate the proposal's structure and references. Local publication can use --unassessed; independent meaning review is a separate step.
  5. Maintain: later checks identify affected explanations. Refresh those explanations while preserving notes and previous snapshots.

Codeclew is not itself a hosted writing model. Your chosen agent writes the narrative and follows its own model and data settings. Registration captures facts; it does not automatically produce a complete architecture explanation.

What each analysis engine contributes

Choose the evidence needed for your question. More modules can improve specific facts, but do not turn a static document into a runtime trace. The installed capability catalogue is authoritative:

clew docs modules list --root ./architecture
clew docs modules show --root ./architecture --id kotlin-k2
clew docs modules list --root ./architecture --service SERVICE_ID
clew doctor repository --repo /path/to/service --committed

Read freshness, review and evidence limits

CURRENT means recorded dependencies still match the checked source. It does not mean the explanation is complete or independently verified. UNASSESSED means separate meaning review has not established the narrative's correctness. Missing authored operations remain coverage gaps.

Evidence limits state what the selected analysis could not establish. They are not service defects. Use each ? by hovering, keyboard focus or clicking for its meaning and next step. A node-budget limit means part of a flow was not explored; an unresolved call means dispatch is unknown; a file-only item means text was retained without structured analysis. K2 may improve language resolution, but cannot supply deployment observations or missing business policy.

Supply knowledge and choose depth

Keep your original description in a Markdown note. Specify its target, date/environment and whether it is a fact, question, intention or correction. Explicitly ask to save it, investigate it, change a declared definition, or update an explanation. Saving a comment alone does not silently rewrite a process or entity.

For a particular method or paragraph, target the containing service section and name the exact focus in the note. Arbitrary source anchors and a browser comment composer are not supported note targets. Select detail by audience, question, scope and required outputs; there is no universal numeric detail setting. The 20 developer runbooks provide reusable examples.

Safe updates and input digests

RETURNED_INPUT_DIGEST is a placeholder for the complete inputDigest in the preceding catalogue list/show response, including sha256:. It prevents a write from overwriting a catalogue that changed after you read it. On conflict, re-read the current record, reconcile changes and use its new digest. Note operations can also require the original note's digest.

Files, privacy and portability

Keep original notes, catalogues, accepted narratives, recorded evidence and publication history in your documentation repository and version control. Generated snapshots are immutable; edit authoring inputs and publish a new snapshot. Bindings and temporary work caches are local. On another laptop, clone the docs and service repositories, rebind each service and check freshness.

User notes are explicit repository content with their provenance and intended associations. Review the documentation repository before sharing it: retained source and operational notes can be private.
