BUNDLED CODECLEW GUIDE

Work locally with Codeclew

This guide and the Codeclew runbooks are included when you initialize a documentation repository. Service explanations, business definitions and operational knowledge come from your repositories and notes.

Start on another laptop

clew --version
clew skill install --agent codex
# For compiler analysis of Kotlin 2.3 projects:
clew pack install kotlin23
clew docs init --root ./architecture --title "Service documentation"

Open architecture/docs/help.html directly, or serve the architecture directory on localhost. For an existing documentation repository, clone it together with its retained evidence and history, then bind each relocated service checkout:

clew docs bind --root ./architecture --service SERVICE_ID --repo /path/to/service
clew docs check --root ./architecture

Add a service, scenario or dataflow

Ask the agent: “Register this local service from its committed source, document its responsibilities, ingress, egress, entities and failure paths. Show gaps and uncertain relationships. Use examples/service-source.json and preserve my original notes.” The examples directory also contains interaction and scenario records.

Use clew docs service --help, clew docs process --help, clew docs entity --help and clew docs view --help for the installed schemas and commands. Ask: “Trace this reservation lifecycle across these services; explain each input, state change, output and failure, and save the scenario.” For a dataflow: “Trace quantity from the incoming payload through validation and persistence to the response; retain source links and mark declared cross-service edges.”

Add a note or comment

Keep the original text in a Markdown file. Tell the agent the target, whether this is a fact, intention or question, and its date and environment. Targets can be a whole service, one service section, a scenario, an entity definition, or a dataflow view. For a particular operation or paragraph, use a section target and describe the exact focus in the note; that text is not a validated code anchor.

For service inventory, section ingress: save this as an open question,
not a confirmed fact: who supplies the reservation ID?
Associate it with the reservation scenario and entity definition.
Then investigate source evidence and update the explanation if supported.

The agent uses docs note import for an external file, or docs note associate for an existing note. It reads current digests before writing, preserves your original wording and prepares an assessment. A saved comment does not by itself rewrite an entity or prove the answer. State whether you want only to save it, answer it, change a definition, or expand the explanation.

What is expected-input-digest?

RETURNED_INPUT_DIGEST is a placeholder. Replace it with the complete inputDigest value returned by the preceding list or show command, including sha256:. It identifies the catalogue version you read and prevents overwriting a concurrent change.

clew docs process list --root .
# Copy the actual inputDigest value from that JSON response.
clew docs process put --root . --input my-process.json \
  --expected-input-digest sha256:ACTUAL_HASH_FROM_THE_RESPONSE

On conflict, read the current record again, reconcile the change and use its new digest. Never reuse an old digest merely to force a write.

Choose the detail you need

Provide the audience, question, service scope, desired depth and what is missing. For example: “For developer onboarding, explain reservation create, adjust and release with API request/response fields, entity states, failure branches, persistence and downstream notifications. Include source links and an operator checklist. Leave unrelated utility methods at inventory depth.” Save this preference as an intention note so future agent work can read it.

Ask the agent to report whether the available source and notes answer each question. Missing deployment settings, business ownership, alert thresholds and recovery approval must remain explicit unknowns. There is no automatic universal detail-level switch.

Publish and inspect evidence

Use docs work prepare/read, docs proposal submit and docs proposal publish --unassessed with the agent to author and publish local explanations. Meaning review stays UNASSESSED until separately reviewed. Generated pages live under docs/generated; preserve originals outside that directory.

Open a service and choose Coverage and evidence → Analysis evidence. Source syntax and optional compiler evidence are reported separately. K2 adds resolved semantic facts only when the configured provider succeeds; it does not prove deployed routing or business meaning.
