DEVELOPER RUNBOOKS

20 everyday documentation tasks

Choose a task, supply the listed inputs, then follow the steps or adapt the example request for your agent. Examples use fictional services and are reusable documentation recipes.

Commands below run from your documentation root unless they initialize it. Replace service IDs and paths with your own. RETURNED_INPUT_DIGEST means the complete inputDigest from the immediately preceding catalogue response, including sha256:. On conflict, re-read and reconcile. JSON inputs are authoring files, not generated HTML.

New to the tool? Start with installation, engine capabilities and supported documentation objects. The CLI commands identify the workflow; the agent prepares evidence-bound selections and proposals using the bundled skill and current returned schemas.

01. Create a documentation workspace

Have ready: A local Codeclew installation and a place for a separate docs repository.

  1. Run docs init with the intended root and title. Open the included help and runbooks before adding any service.
  2. Initialize Git for the new documentation repository if needed. Keep its catalogue, notes and accepted publications in version control.
  3. Install the bundled agent skill, then use the following recipes from the documentation root.

Example request

Set up a local documentation workspace named System architecture. Explain where source registrations, notes and published pages live. Do not invent any services.

Commands used

clew docs init --root ./architecture --title "System architecture"
clew skill install --agent codex

Expected result: An initialized repository containing docs/help.html, docs/runbooks.html and registration examples.

02. Add a new service

Have ready: A local service checkout, its credential-free Git remote, committed ref, language and source/configuration paths.

  1. Copy examples/service-source.json to an authoring file and replace the placeholder identity, title, repository URL, targetRef, language and source roots.
  2. Read the catalogue digest, save the registration, bind the checkout and capture evidence. service add also updates an existing record with the same repository identity.
  3. Inspect discovered entry points and gaps before asking for a narrative. Adding a service alone does not explain it.

Example request

Register the local orders service from its committed main branch. Include production source, relevant configuration and migrations. Capture evidence and show its incoming and outgoing boundaries, without inventing deployed connections.

Commands used

clew docs service list --root .
clew docs service add --root . --input authoring/orders-service.json --expected-input-digest RETURNED_INPUT_DIGEST
clew docs bind --root . --service orders --repo /path/to/orders
clew docs check --root . --service orders

Expected result: A named service, a local binding and a checked source inventory.

03. Write the first service explanation

Have ready: A registered service and a successful or explicitly partial source capture.

  1. State the intended audience and the service ID. Ask the agent to inspect current context, including omitted pages and declared gaps.
  2. Have it prepare bounded authoring work and explain overview, responsibilities, entities, ingress and egress.
  3. Review source-linked claims; publish the checked proposal locally with meaning review UNASSESSED if no separate reviewer is configured.

Example request

Document orders for a new backend engineer. Explain its purpose, business objects, triggers, outputs and failure paths. Use current registered evidence and preserve unknowns. Prepare and publish the supported service sections locally as UNASSESSED.

Commands used

clew docs context --root . --service orders --format compact --limit 100
clew docs work --help
clew docs proposal --help

Expected result: Readable service sections with source references and explicit unauthored operations.

04. Add a sequence diagram

Have ready: A concrete operation or process trigger and the source declaration that starts it.

  1. Name the trigger, root service/operation, participants and desired outcomes. Have the agent build a process definition from the returned source identity.
  2. Inspect the candidate definition before saving. Read the process-list inputDigest and save it with process put.
  3. Prepare the overview and detailed process work. Author explanations for the diagram steps, decisions, returns and async boundaries; publish the checked proposal. The reader renders the sequence from accepted narrative and evidence.

Example request

Create a sequence diagram for placing an order, starting at the orders HTTP handler. Explain validation, persistence, outgoing messages and failure branches. Show asynchronous boundaries and link every supported step to source. Save it as order-placement and publish its explanation.

Commands used

clew docs process inspect --root . --input authoring/order-placement.json
clew docs process list --root .
clew docs process put --root . --input authoring/order-placement.json --expected-input-digest RETURNED_INPUT_DIGEST
clew docs process prepare --root . --id order-placement --overview

Expected result: A saved process with an overview and evidence-linked detailed sequence; unresolved call targets remain explicit.

05. Explain a path across services

Have ready: The service IDs, a business question and candidate producer/consumer or caller/server boundaries.

  1. Register and bind each service involved. Inspect their committed contracts and configuration.
  2. Declare the specific HTTP or Kafka interactions through docs interaction; retain origin and uncertainty.
  3. Save a process rooted at an actual entry point. Explain each independently evidenced stage; a matching topic or route is not proof of deployed delivery.

Example request

Explain how an order-created message reaches fulfillment. Compare the producer and consumer payloads and topic configuration. Save supported declarations and a process overview, keeping missing deployment settings and unmatched stages explicit.

Commands used

clew docs interaction list --root .
clew docs interaction candidates --help
clew docs interaction put --help
clew docs process inspect --root . --input authoring/order-to-fulfillment.json

Expected result: A navigable multi-service explanation separating declared links, source-supported stages and runtime unknowns.

06. Add an OpenAPI contract

Have ready: A committed OpenAPI 3.0.0 or 3.0.3 document and all local referenced files.

  1. Add contractFiles to the service registration, including every required local reference. Preserve the service ID and repository identity.
  2. Read the latest service catalogue digest and save the updated registration with service add. Run docs check.
  3. Ask the agent to explain parameters, request bodies, responses, constraints, security and errors. Inspect unmatched declarations and reference gaps in the reader.

Example request

Add api/openapi.yaml and api/schemas.yaml to the orders contract registration. Explain the create-order request, successful response and error responses. Compare declared routes with implementation evidence; do not assume the implementation enforces every schema constraint.

Commands used

clew docs service list --root .
clew docs service add --root . --input authoring/orders-with-contract.json --expected-input-digest RETURNED_INPUT_DIGEST
clew docs check --root . --service orders

Expected result: Declared contract cards and an authored contract explanation, including unsupported references or source mismatches.

07. Describe a contract when no OpenAPI exists

Have ready: A named HTTP operation, message type or file import boundary and its selected source.

  1. Ask the agent to inspect the handler, DTO, validation and sender/consumer code together.
  2. Describe observed fields, defaults, required checks, outputs and errors with exact source links. Preserve custom serializers or missing dependencies as uncertainties.
  3. Publish a focused operation/process explanation. If you also create an OpenAPI file, label it a new declaration and commit/register it separately.

Example request

Document the order-created message contract from its producer DTO, serializer and fulfillment consumer. Include field meanings, optional values, validation, key/header usage and failure handling. Mark any business meanings not established by source.

Commands used

clew docs context --root . --service orders --format compact --limit 100
clew docs context --help

Expected result: An implementation-based contract description, distinguishable from a separately declared API specification.

08. Define a domain entity

Have ready: A stable business name, meaning, identifiers and candidate service/DTO/table relations.

  1. Describe the domain concept and its owner or provenance. Do not infer business identity solely from matching class names.
  2. Have the agent prepare the supported entity record and read the catalogue digest. Save through docs entity put.
  3. Associate the entity with the processes and service explanations that use it; refresh the affected authoring work.

Example request

Define entity:order as a customer purchase request. Record its business identity separately from OrderRequest and the orders table. Link only source-supported representations and keep ownership questions explicit.

Commands used

clew docs entity list --root .
clew docs entity put --root . --input authoring/order-entity.json --expected-input-digest RETURNED_INPUT_DIGEST

Expected result: A reusable declared entity definition with proposed, inspectable relationships.

09. Add your own explanation to an entity

Have ready: A Markdown description, entity ID, date and whether it is policy, fact or an open question.

  1. Save the original text in notes and associate it with entity:ID. Preserve the original wording.
  2. Say whether you only want to retain the note or also change the declared entity definition.
  3. If requesting a definition change, have the agent reconcile the text with existing declarations and source, save the entity record using the current digest, then refresh affected explanations.

Example request

Attach notes/order-policy.md to entity:order as a dated business policy. Preserve the original. Update the declared definition to reflect this policy, and separately report any contradictions with current implementation.

Commands used

clew docs note associate --help
clew docs entity list --root .
clew docs entity put --help

Expected result: A preserved original note plus an explicit definition update when requested; human policy remains distinguishable from source observations.

10. Add your own explanation or question to a process

Have ready: A process/scenario ID and the exact text to retain.

  1. Store the text as a note with a scenario:ID association. State whether it is a question, correction, observation or intended behavior.
  2. Ask explicitly to save only, investigate, or revise the process explanation.
  3. For an explanation change, prepare new process work and publish a checked proposal; do not edit a frozen HTML snapshot.

Example request

Attach this question to scenario:order-placement: can payment succeed when order persistence fails? Preserve it as a question, inspect the relevant source, and update the explanation with supported outcomes and remaining unknowns.

Commands used

clew docs process show --root . --id order-placement
clew docs note associate --help
clew docs process prepare --root . --id order-placement --overview

Expected result: A comment linked to the process and, if requested, a revised evidence-linked explanation.

11. Comment on a service or one part of it

Have ready: A service ID, optional standard section, and a note file.

  1. Use service:ID for the whole service or service:ID/section-ingress, section-egress, section-entities, section-responsibilities or section-overview for a section.
  2. For a particular method or paragraph, identify the exact focus in the note. Arbitrary source/paragraph anchors are not supported note targets.
  3. Import an external note or associate an existing repository note. Read both catalogue and note digests when the command requires them.

Example request

Attach notes/order-errors.md to service:orders/section-ingress. Its focus is the create-order handler error responses. Save my original wording, investigate each question and keep unsupported answers explicit.

Commands used

clew docs note list --root .
clew docs note inspect --help
clew docs note import --help
clew docs note associate --help

Expected result: A protected original note with a visible typed association; no browser discussion thread is implied.

12. Make an explanation more detailed

Have ready: An existing object plus an audience, question, scope and required outputs.

  1. Specify which operations or branches need detail and which can remain overview-only. Save that preference as an intention note if it should persist.
  2. Ask the agent to inspect whether existing evidence answers the questions; expand registered source roots or obtain owner notes where needed.
  3. Prepare focused operation/process work rather than overloading short service summaries. Publish the revised explanation with unresolved points visible.

Example request

Deepen order-placement for an engineer implementing a client. Include request/response examples, validation branches, transaction boundaries, retries and resulting entity states. Keep unrelated helper methods at inventory depth. Report which requested details lack evidence.

Commands used

clew docs process prepare --root . --id order-placement
clew docs work --help

Expected result: A focused, deeper explanation driven by explicit questions. There is no universal numeric detail-level switch.

13. Add an entity dataflow

Have ready: A domain entity, input representation, output representation and transformation question.

  1. Define or reuse the domain identity. Select the service scope and source-backed representations.
  2. Ask the agent to save a docs view definition using an available view module, then prepare its work.
  3. Explain reads, transformations, writes and transfers; distinguish declared domain mappings and cross-service edges from compiler-established facts.

Example request

Trace order quantity from the request DTO through validation and mapping to persistence and the outgoing event. Save an entity dataflow, explain each transformation and show source evidence and unknown transfers.

Commands used

clew docs view modules --root .
clew docs view put --help
clew docs view prepare --help

Expected result: A maintained entity dataflow with readable node/edge meanings, source links and explicit authority.

14. Split a large process into useful child views

Have ready: A process whose flow is too large or reports a node/depth limit.

  1. Identify independently understandable stages and choose a concrete root for each child process.
  2. Author and publish the child explanations first. Link their accepted versions from the parent definition.
  3. Refresh the parent overview and inspect its captured child versions. Increasing a traversal budget alone does not make an explanation clearer.

Example request

Split order-placement into validation, persistence and asynchronous fulfillment. Create focused child processes, publish supported explanations, and link their accepted versions into the parent overview. Preserve the async boundary.

Commands used

clew docs process list --root .
clew docs process show --root . --id order-placement
clew docs process put --help
clew docs process prepare --root . --id order-placement --overview

Expected result: Smaller diagrams with a composed overview and explicit freshness of linked child explanations.

15. Enable Kotlin compiler evidence

Have ready: A Kotlin service, admitted profile/compilation and the required toolchain/dependencies.

  1. Use repository doctor to inspect project compatibility and an exact available local target ref. Install kotlin23 for Kotlin 2.3 when needed.
  2. Have the agent update the service semantic module selection to kotlin-k2 with the admitted profile and compilation. Do not combine explicit modules with legacy source.semantic configuration.
  3. Check the service and inspect Analysis evidence. Refresh affected explanations; an installed pack alone does not activate compiler enrichment.

Example request

Inspect whether orders can use K2. Report the admitted profile and compilation, enable the supported Kotlin semantic module for this service, and show concrete mapped API types and remaining unresolved facts. Refresh affected documentation.

Commands used

clew pack install kotlin23
clew doctor repository --repo /path/to/orders --committed
clew docs modules show --root . --id kotlin-k2 --service orders
clew docs check --root . --service orders

Expected result: Compiler provider status and supported semantic facts, with partial mapping and runtime limits retained.

16. Add Java compiler and Spring boundary evidence

Have ready: A Java service, its project-native toolchain and relevant Spring sources.

  1. Inspect repository admission and the module catalogue. Configure an admitted Javac semantic selection in the source-syntax service registration.
  2. Capture the service. Spring consumes supported source/compiler annotation facts; it is not a separate compiler to guess or install.
  3. Inspect HTTP handlers, Kafka listeners, scheduled methods and outbound Feign declarations. Keep conditional activation and deployment wiring unverified unless separately observed.

Example request

Use the admitted Javac provider for billing and inspect Spring boundary evidence. Separate inbound controllers, scheduled handlers and outbound clients. Explain what compiler facts improved and which runtime conditions remain unknown.

Commands used

clew doctor repository --repo /path/to/billing --committed
clew docs modules show --root . --id javac --service billing
clew docs modules show --root . --id spring --service billing
clew docs check --root . --service billing

Expected result: Stronger Java facts and supported Spring boundary interpretation with explicit activation limits.

17. Refresh docs after source changes

Have ready: A new committed source revision and existing documentation.

  1. Run docs check and inspect affected fragments with docs changes. Selective checks leave other services explicitly unchecked.
  2. Ask the agent to refresh the affected roots from current evidence and preserve original notes. Review source versus business-policy differences.
  3. Publish new checked proposals. A status-only refresh updates freshness without authoring a new explanation; it cannot make stale prose current by itself.

Example request

Check the new orders commit. Explain which documented claims changed, refresh only affected explanations, preserve my notes and retain explicit gaps. Do not rewrite unrelated sections.

Commands used

clew docs check --root .
clew docs changes --root . --limit 100
clew docs refresh --root . --status-only

Expected result: New explanations where needed, retained history and honest freshness for unchanged or unresolved material.

18. Move the documentation to another laptop

Have ready: The docs Git repository or bundle and separate service checkouts.

  1. Transfer the complete documentation repository, including accepted narratives, evidence and immutable history. Install Codeclew and its agent skill.
  2. Clone the service repositories and bind their new local paths. Do not copy temporary work caches as a substitute for binding.
  3. Check the selected commits. Changed source may correctly produce stale explanations; existing pages remain readable offline.

Example request

Bind this documentation repository to the service clones under my workspace. Check source freshness, report mismatched revisions and leave original notes and history intact.

Commands used

clew docs bind --root . --service orders --repo /new/path/to/orders
clew docs check --root .

Expected result: A portable, locally usable knowledge base with recreated bindings and checked source revisions.

19. Write a service incident runbook

Have ready: A symptom, environment/date, affected service, and any actual logs or owner guidance.

  1. Associate the original operational observations with the service or process. Keep sensitive deployment details in the appropriate private repository.
  2. Ask for diagnostic steps, expected observations, recovery prerequisites, authorization and post-recovery checks.
  3. Separate source-supported behavior, observed deployment facts and proposed procedures. Missing owners, thresholds or replay policies remain explicit questions.

Example request

Create a runbook for delayed order-created delivery. Trace enqueue, send, retry and acknowledgement stages. Use source plus my dated staging observations; include expected checks and recovery prerequisites without inventing production commands.

Commands used

clew docs note import --help
clew docs process prepare --root . --id order-placement --overview

Expected result: A service-specific operational procedure with evidence, provenance and unresolved operational inputs.

20. Publish, inspect history and share the result

Have ready: A READY proposal with current evidence and a reviewed publication destination.

  1. Publish the accepted local proposal with --unassessed unless a separate configured meaning review establishes a stronger state. Open the reader and inspect source links, diagrams and remaining gaps.
  2. Use history to compare retained publications. Rendered HTML, Markdown and diagram exports come from the accepted explanation; do not edit immutable output.
  3. Commit the documentation inputs and retained publication. Review private source and notes before transferring or hosting the repository. A local server is sufficient for a team walkthrough on your machine.

Example request

Publish this READY documentation proposal locally as UNASSESSED. Show the updated service, sequence and dataflow pages, explain freshness and remaining coverage gaps, and summarize the Git diff for review.

Commands used

clew docs proposal publish --root . --proposal RETURNED_PROPOSAL_ID --unassessed
clew docs history --help
clew docs render --root .
python3 -m http.server 8767 --bind 127.0.0.1

Expected result: An offline publication, retained history and a versioned repository ready for the intended sharing scope.
