reproduction and inspect the source behind its result. Keep six active top-level
pages at existing URLs; introduce no new top-level feature pages.

## Three cases before a feature catalogue

**Find the code.** Use a public committed Clew checkout and a named Rust function
such as `fair_fact_selection`. Show repository discovery, a real installed-release
query, the returned exact declaration/source, and a short engineering answer.
Add one deliberate no-match/ABSTAIN case with a next action. The old 0.3.1
`nav_query` implementation tour remains historical evidence. Explain exact-name
selection only where it changes the reader's action.

**Create a first document.** Start with the real Python script
`scripts/build_cli_documentation.py`: “What does --check verify, and when does it
invoke Graphviz?” Use `clew docs init` and the starter bundled by the final
installed release. Show the actual saved packet/proposal paths and an explicit
request to the current agent. Submit, inspect structural readiness and publish
locally with `--unassessed`; show the resulting overview and one source link.
The first result retains UNASSESSED meaning and visible unwritten gaps. Ask the
saved-source question without recapturing or republishing. A follow-up update
must demonstrate changed source plus preservation of an owner note, unrelated
content and previous publication bytes. Optional linked-process, review and
compiler paths follow the first result and need their own observed useful case.
Do not reuse an experimental method draft as proof of a published workflow.

**Review saved edits.** Keep the approachable Pricing fixture: body 1→3 with a
staged 2, `label(Int)`→`label(Long)`, and a removed call. First show what changed,
why a consumer deserves inspection, and what to check next. Put the graph,
exact before/after source and coverage behind those decisions. Supply fixture
setup, a fresh final-release run and an explicit freshness check after another
saved edit. Inspection does not execute project tests; main/test scope and
Kotlin compiler versus Rust syntax limits remain adjacent to the result.

Each task page has one question, prerequisites, an executable public case,
expected output grounded in a real run, one source-inspection action, the relevant
limit, and a next action. Replace the long documentation feature catalogue with
this sequence and small optional links to versioned reference material.

sections were authored/reviewed with installed 0.13.7 from source
`fd82a763fb5b38083fc3f298aee5ee116c906e21`, with PARTIAL publication, 15
worker/NOTE gaps, UNVERIFIED pinned freshness and UNKNOWN runtime. Its qualified

provenance reportedly verified that `ef418…` was emitted by installed 0.13.10 with
official byte equivalence. Its public manifest itself does not identify a CLI
runtime. A newer reader does not rewrite the accepted source narrative's authority.

New public dogfood must use the final published installed release and record its
version/runtime, public source revision, scope, returned status and publication
identity. If the final tag supersedes 0.13.10, use that tag. Generate a fresh
`examples/current-workflow/docs/` tree through supported native commands. Keep
all old `examples/codeclew-source/docs/generated/<id>/` bytes and the original
Java draft/provenance unchanged. Keep historical reproduction templates and
measurements under their original authority; do not transfer their timing or
candidate qualifications to current marketing claims.

The old generated root has an observed coherence defect: index/catalog link into
`ef418…`, help/runbooks into `aa52…`, while history lists the two released
snapshots. There is no detected meta-refresh or JavaScript location redirect;
the mismatch is navigation link targeting. Check every fresh native root route
and its Home/Browse/Help/Runbooks/search links against the intended bundle. If the
defect recurs, fix the renderer and generate new output; do not hand-patch native
