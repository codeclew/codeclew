# Codeclew v0.13.1 — experimental internal-process draft

This patch is the first binary release of the 0.13 series. The v0.13.0
candidate did not publish assets because its Linux CI gate failed. The patch
checks a prior generic Work run before platform-specific driver admission, so
both normal recovery and `--new-run` report `RECOVERY_MODE_MISMATCH` consistently.
It preserves driver isolation, immutable bindings and budget rules.

The release adds a narrow draft path for explaining one compiler-backed
internal Java method. The public example selects
`TaskStateTransitions.promote(Task, Instant)` in the `:/main` Maven
compilation. It is a source-local decision explanation, not a complete dispatch
workflow or a publication feature.

## Process-intent citations and saved-result recovery

- Reader-packet citation validation now accounts for the displayed
  `processIntent.definitionReference` and each declared continuation's
  `reference`. The exact citation-set check remains in place: malformed,
  empty, unknown and extra labels are rejected. These labels retain their
  declared authority. A process definition records user intention, and a
  declared continuation is not evidence that a call executed.
- A terminal draft recorded as `ANSWER_INVALID` may revalidate only its
  digest-bound saved author result. The selected invocation, immutable input and
  durable result are checked before recovery proceeds. Recovery does not call
  the author again; a result that still fails answer validation remains invalid.
- A valid structured draft produces local `answer.json`, `operation.md` and
  `index.html` views beneath `.codeclew/drafts/WORK_ID`. The renderer can show
  the authored decision tree as pseudocode. Separately, the source-local
  process-flow diagram is projected from retained source syntax, not from the
  authored steps. Neither view is a runtime trace. The command creates no
  proposal, review or publication.

The [reproducible recipe](https://github.com/codeclew/codeclew/blob/v0.13.1/docs/operations/task-promotion-draft.md)
uses public fixture inputs for the [service](https://github.com/codeclew/codeclew/blob/v0.13.1/fixtures/documentation-internal-process/documentation/service.json)
and [process](https://github.com/codeclew/codeclew/blob/v0.13.1/fixtures/documentation-internal-process/documentation/process.json).
The author configuration remains operator-selected; the
[service-documentation skill](https://github.com/codeclew/codeclew/blob/v0.13.1/skills/codeclew/references/service-documentation.md#draft-one-internal-service-process-explanation)
defines its schema and requirements. Codeclew does not select a model, provide
credentials or authorize a budget by default.

The configured stdio author path requires macOS Seatbelt. Linux packages retain
source capture and the external structured-answer renderer; this example does
not qualify author execution on Linux.

## Stage diagnostics

Documentation progress events on stderr now include wall-clock timestamps and
monotonic durations. Operation drafts distinguish packet preparation, driver
admission and startup, request delivery, response waiting, validation/rendering
and output writes, with a heartbeat every five seconds. JSON results remain on
stdout. See [diagnosing a draft run](https://github.com/codeclew/codeclew/blob/v0.13.1/docs/operations/field-documentation.md#diagnose-a-draft-run).

## Scope and qualification

The example explains only the source-local decision in `promote`. Its retained
source can show repository-interface calls, but it cannot establish that those
calls commit persistent state or that any runtime caller reaches the method.
Later dispatch, external effects, actual persistence and deployed behavior are
outside this example. Compiler-backed candidates and optional graph output keep
their saved-evidence authority and do not establish execution order or complete
runtime reachability.

The checked-in [sample provenance](https://github.com/codeclew/codeclew/blob/v0.13.1/fixtures/documentation-internal-process/documentation/sample/provenance.json)
records one author call (164.078 seconds) and its native saved-result replay.
Replay validated the same Work, run, invocation and raw answer; the saved-result
file hash and attempt/accounting remained unchanged, with no new author
dispatch. An independent GPT-6.1 Sol/High source-FIT review and a Chrome
browser review at desktop 1365 px and mobile 390 px accepted this scenario; it confirmed
the citation links. The result remains `DRAFT` / `UNREVIEWED` and unpublished.
This evidence covers one source-local method and rendered sample, not complete
workflow qualification or runtime and persistence claims. The single-run
timing is diagnostic, not a latency promise.

The checked-in sample's `index.html` can be opened from a local checkout;
GitHub's file view does not render it as a page. The sample answer and reader
packet are bound to the original Work and snapshot and are not replay inputs for
a fresh Work. Timing reports should retain CLI phase diagnostics and name the
release, fixture revision, host, configured model and cache condition.

Reproduce the example from the checked-in public fixture in a separate clean
repository. Its `https://example.invalid/dispatch-fixture` origin is synthetic
metadata and is not a fetch or push target. Keep private source paths, raw
experiment inputs and credentials out of public artifacts.
