# Codeclew v0.9.0 — reusable analysis and retained documentation

This release prepares Codeclew for a field trial on large multi-repository
projects. It reduces repeated compiler analysis, batches compatible Java Maven
builds, and lets documentation consumers work from saved evidence without
implicitly starting indexing.

## Analysis and recovery

- Compatible Java Maven main/test selections share reactor build invocations.
  Each selected compilation retains its own source, classpath and processor
  authority. Changes to admitted source/classpath inputs during capture are
  rejected before publication.
- Eligible committed Java inputs use a sealed source/classpath/JDK image and
  durable per-compilation checkpoints. A new session with equal complete inputs
  reuses the original verified result. Incomplete work remains retryable.
- Kotlin retains results across fresh sessions and equal source trees at different
  revisions. Source edits preserve compatible build configuration and classpath
  snapshots. Compiler-generated label and ordering instability is normalized.
- Compiled Java outputs from different modules no longer overwrite each other
  when the analysis workspace is sealed.
- Up to 128 explicitly selected compilation scopes are supported. This is an
  admission limit, not a guarantee for arbitrary source volume or memory demand.

## Documentation and storage

- Saved checks, work creation and rendering consume retained evidence by default.
  Explicit refresh checks current sources. Changed participants make evidence
  stale or unverified instead of silently starting producers.
- Work manifests reference shared evidence instead of copying large dependency
  maps into every job. Agent context and dependency pages avoid repeated payloads.
- Snapshot pins retain shared immutable objects without copying them.
- New documentation objects avoid redundant metadata sidecars; supported
  maintenance can compact existing sidecars.
- Closed Java analysis copies have managed process leases. `storage gc --apply`
  can reclaim abandoned copies after all Java users exit, while retaining saved
  analysis checkpoints.
- Rendering preserves manual prose and supports offline retained evidence.
  Paginated checks retain their public schema and incomplete-result exit status.

## Trial boundaries

Java checkpoint reuse in this release is a post-model optimization for qualified
committed, no-processor, non-module-mode inputs on supported macOS/JDK 21 images.
Fresh Maven model extraction and reactor builds still run. Working-tree,
annotation-processor, transformed-source or unqualified execution inputs keep
their existing execution path and report why durable analysis reuse is ineligible.
A release/runtime change can invalidate reuse; old evidence is never relabeled
current merely because the release changed.

A synthetic native reactor with 70 main scopes and 700 small Java files completed
in 258.4 seconds with warm Maven dependencies on the development host. Sampled
process-tree RSS peaked near 620 MiB. This checks scope admission and a particular
fixture, not the source volume, processors or topology of inaccessible customer
repositories. A three-scope fresh-session repeat launched zero analyzers after
three initial analyzer launches; Maven still launched seven processes each time.
These are individual qualification observations, not a general speedup estimate.
The measurements used a frozen development candidate; final packaging and
subsequent scratch-lifecycle changes are validated separately.

Retained history, runtime components and dependency caches have separate
lifetimes. This release does not promise automatic disk-usage plateaus or universal
resource admission. Some full-store diagnostics still have bounded inventory
limits. General processor-input closure, resource-based limits and additional
pluggable document generators remain follow-up work.

## Field-trial steps

1. Update the installed launcher; verify `clew --version` and
   `clew doctor attach --human`. Keep the original repositories and diagnostic
   exports intact.
2. Use `clew doctor repository` and the existing source-documentation workflow
   to inspect the actual compilation selection. Include test scopes explicitly
   when needed; the trial limit is 128 scopes.
3. Perform an initial capture. For qualified committed inputs, repeat through a
   fresh session without changing inputs and inspect the reuse observation.
   Separately read or render the saved documentation snapshot; these consumer
   operations should not start a build or analyzer.
4. If the trial fails, retain the version/runtime identity, selected scopes,
   eligibility or reuse reason, phase timings and sanitized error. Non-cacheable
   processor input is an explicit boundary; do not remove required processors
   or edit private state files to obtain a cache hit.
