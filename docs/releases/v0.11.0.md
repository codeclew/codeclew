# Codeclew v0.11.0 — internal-flow visuals and saved-capture recovery

This release brings evidence-bound internal-flow diagrams, dependency maps and
decision tables into generated documentation. Authors can publish them with
service responsibilities or operation explanations using saved evidence, without
a separate visual atlas or another indexing pass.

## Useful visuals in the native reader

- The service overview presents accepted responsibilities, domain information,
  entry points and external calls before detailed diagrams. Missing content and
  discovery limits remain visible; an empty inventory does not prove absence.
- Author jobs ask section-specific reader questions and distinguish business
  objects from DTOs, local fragments from entry-rooted scenarios, and queue
  insertion from execution or completion. These prompts guide interpretation;
  they do not replace source review or add unsupported analyzer coverage.
- Closed proposal records accept `execution-flow`, `dependency-map` and
  `decision-table` visuals with source-bound purpose, scope and semantic claims.
  Layout and local rendering are owned by Codeclew; authors do not supply raw
  HTML, script or imported Mermaid.
- Decision tables can link to an execution-flow node in the same operation.
  Local decisions without a proven parent retain their scope and missing-link
  limitation. Structural dependency maps remain distinct from execution order.
- `FIRST`, `UNIQUE` and `UNKNOWN` policies require an evidence-bound explanation.
  First match chooses one row; it does not order multiple tables. Later execution
  failures remain separate from pre-action selection rules.
- Visuals are published and retained atomically with their containing operation,
  including its evidence, source freshness and meaning-review status. They do not
  have an independent artifact acceptance lifecycle. Unassessed prose cannot
  become verified merely by adding a diagram.
- Updating an operation with existing visuals requires an explicit replacement
  array. Omitting it cannot silently erase diagrams; an explicit empty array
  removes them from the new version while preserving history.

Use the [native visual authoring workflow](../operations/field-documentation.md#publish-internal-flows-and-decisions-in-service-pages)
with general Work/proposal authoring or a configured process-overview job. The
narrow `section-author-v1` job still produces only a summary. Source interpretation
and selecting useful process boundaries remain authoring work; capture alone
does not generate complete business explanations.

## Continue from saved work

- Section Work starts with a bounded orientation packet, relevant retained
  evidence references and an explicit discovery index. It no longer requires
  reading every captured dependency before a section can be authored. Deferred
  evidence remains available through registered reads, and its conservative
  change-tracking scope is preserved.
- `docs snapshot recover` assembles an explicit historical snapshot from intact
  current-format service captures after a check failed before saving its final
  snapshot. Recovery requires matching declarations and explicit capture
  manifests; it does not access source checkouts or run compilers.
- Checks diagnose a missing selected publication baseline before starting source
  acquisition. Restore the missing bundle or explicitly preserve and detach the
  discarded publication; another compiler run cannot repair missing bindings.
- Recovery leaves latest-check unchanged and does not assert current source
  freshness. Context, Work and rendering continue from the returned snapshot.
- Within the supported stored-data format, upgrading the HTML reader no longer
  invalidates saved evidence or requires reindexing. Historical renderer identity
  remains recorded; the next publication uses the current reader.
- Publishing one service no longer invalidates independently prepared sibling
  Work merely by creating its empty placeholder page. Authored changes and custom
  gap descriptions still trigger real write conflicts.

## Less duplicated publication evidence

Proposal records reference their saved Work influence rather than serializing the
whole map again. Portable publications share identical influence maps between
accepted operations and retain distinct historical evidence when needed. Updating
one operation preserves the evidence still required by its siblings. These
changes reduce duplication; they do not remove necessary history or promise
constant storage regardless of retained versions.

## Boundaries and validation

The reader does not automatically discover every internal process, prove that a
decision table faithfully models source, or establish runtime behavior. Unknown
branches, omitted helpers and partial service coverage must remain visible. The
new tables are documentation, not executable DMN. A universal generator plugin
SDK and independently reviewed artifact lifecycle are outside this release.

Recovery accepts current formats only; it is not a migration for old roots.
Prepared Work still requires compatible declarations and intact recorded evidence.
The existing compilation-scope and evidence budgets remain in force.

Regression coverage includes typed visual validation, native reader navigation
and escaping, source-bound publication and offline replay with the original
checkout removed, and sibling-publication conflict handling. Source freshness
and meaning review remain separate from these structural and lifecycle checks.
The release pipeline verifies the product and qualifies packaged builds for
macOS arm64/x86_64 and Linux x86_64 before publishing assets.
