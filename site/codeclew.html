Source-linked guide · Codeclew 0.13.24

Capture once. Publish by choice.

Turn a selected source scope into a saved Work, prepare and read its evidence, submit proposed prose, then publish it as a separate, explicit step. Keep the check, Work, proposal and publication references together so each handoff can be traced.

The documentation CLI routes checks, Work, proposals and rendering through a phase-labeled progress wrapper. The source-linked workflow below follows those command families. Command overview · Run declaration

Native evidence index · Full source index · Verification record

1. Capture one selected source scope

Input: a repository and an explicit set of selected services. Output: the check result and a saved snapshot reference. In source order, the capture operation acquires the repository run lock, checks the selection, saves the snapshot, and returns both values. Inference: save that snapshot reference for Work preparation; a separate freshness result should not be mistaken for the presence or absence of captured evidence.

Confirmed result: one check returned CHECKED while freshness was UNRESOLVED with reason MISSING_BASELINE (exit code 3); an immutable snapshot was still returned. Treat the missing baseline as an unresolved comparison, not as a freshness pass.

Capture overview · run_and_save_selected declaration

2. Prepare and read a saved Work

Input: a subject and Work request, with the saved snapshot reference. The request selects an audience and context profile. For process-graph-v1, the source requires an explicit saved snapshot and states that it performs no source capture. Preparation reads retained evidence, validates the request and registered inputs, assembles exact handles and obligations, stores the Work, then returns its ID with the initial read. If repository declarations or external inputs change during preparation, the final consistency checks reject the Work instead of storing that mixed view. Source order: validate → load snapshot → construct Work → persist → return first page.

Read input: the saved Work ID and a selection. The read entry point loads that Work before requesting the selected page. The confirmed prepare/read steps completed. One oversized dependency read returned ITEM_EXCEEDS_WORK_BYTE_BUDGET with its item reference; a successful part-read continuation was not observed, so keep the reference and verify the available continuation before relying on it.

Work preparation overview · prepare_with_snapshot declaration · Work read overview · read declaration

3. Submit proposed prose and inspect its status

Input: the Work ID and a structured proposal. Submission reloads the Work, checks that it is current, digests its read state, validates the edit context and materializes the narrative. It reports missing initial reads, required inputs or untracked reads as repair diagnostics. In source order, the proposal artifact is written only after a second read-digest check; if Work reads changed during submission, the call returns an error and asks for a retry.

Output: a stored proposal with NEEDS_REPAIR, READY_WITH_LIMITATIONS or READY_FOR_REVIEW. These statuses describe context and declared limitations; they do not amount to formal meaning acceptance. The proposal records meaningReview: UNASSESSED, and submitting does not publish it.

Proposal overview · submit declaration

4. Publish as a separate action

Input: the proposal ID. Publication reloads its Work, verifies currentness, and compares the current read digest with the digest saved in the proposal. If reads have changed, it rejects publication and requires a new submission. If the proposal has canonical content and the checks pass, it hands the narrative to the renderer. Inference: the gate ties publication to the submitted Work state; it does not certify the prose's meaning or runtime effects.

The renderer builds page and status files, commits the resulting bundle, and returns a bundle reference and docs/index.html. Its status may be RENDERED or PARTIAL, and its response keeps runtime UNKNOWN. Publication explicitly leaves meaningReview: UNASSESSED. The resulting pages are documentation outputs, not evidence that a call succeeded or a service delivered work.

Publication overview · Publish match arm in proposals::run · Renderer overview · publish_internal_phases declaration

5. Retain and recover the evidence trail

Keep: the snapshot, Work, proposal and bundle references together. The snapshot interface provides pin, show, list, unpin and recover actions. Recovery accepts existing capture references, or an export together with its source-snapshot reference; supplying only one of the paired export inputs is rejected. Inference: verify the pin or recovery result before discarding the original reference.

The supplied recovery source shows command routing only. It does not include the recovery helpers or a confirmed successful restore, so this guide does not claim which files a recovery recreates or that a recovery completed.

Read the evidence at its boundary

These Rust dossiers retain syntax and source, not compiler-resolved call targets, complete statement effects or a closed data-flow model. The question-mark operator, loops, closures and nested callables, macros, configuration-gated code and CFG behavior retain explicit gaps. Follow the linked declarations for source order; do not infer a callee's behavior, complete control flow, a runtime commit or delivery from them.

Observed in the confirmed CLI path: the check and snapshot result, successful Work preparation and read, and one oversized-read error. Proposal, publication and recovery branches here are source-described workflows; that does not claim every branch was executed.
