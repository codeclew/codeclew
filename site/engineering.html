What Codeclew gives you

Use Codeclew to turn an engineering question into a bounded, inspectable account of the relevant code: where it starts, what the captured source supports, and where the answer stops.

A code investigation tool for engineers and agents

Codeclew is a local CLI that captures code evidence for a coding agent. It can help find an exact declaration, explain behavior, assess selected changes, prepare source-linked documentation, and carry out admitted changes. The agent interprets the evidence; Codeclew checks identities, source bindings, limits and the supported operation. Neither a confident explanation nor a passed binding check substitutes for testing the running application.

You can ask about one method, a set of related functions, or a declared interaction between services. A computation thread is the question's path through that code: the chosen starting point, relevant calls and branches, selected effects, and the boundaries of the available evidence. It can fit inside one method.

One question, from inputs to an answer

Illustrative example — fictional checkout and inventory services. This is a reading model, not an extracted Codeclew result, qualified fixture or runtime trace.

Question: “When may checkout report acceptance, and does that mean stock is reserved?”

  1. Provide the scope. Select the checkout request handler at revision A. Supply its project/module and toolchain so the supported analyzer can capture it. To investigate the receiving service, also supply the inventory repository at revision B and an explicit proposed HTTP relationship.
  2. Read the local source first. Suppose the fictional handler rejects invalid quantities, awaits a reservation call, and returns the upstream result. An answer can identify those conditions and returns with source references. It cannot turn the client call into proof of a database reservation.
  3. Cross the handoff deliberately. If the inventory handler is captured, inspect its own branches, persistence call and response. Keep the relationship to that handler labelled as declared or inferred unless the corresponding authority actually establishes it. If the receiver is absent, the useful result is “caller behavior known; receiver behavior not captured,” plus the missing input.
  4. Separate the outcomes. A receiver's local accepted response, a database commit, a staged event, message delivery and a customer-visible result are different claims. Keep each claim's evidence or explicit unknown. Listing them in a document does not establish that all happened for one request.

Expected artifact: a bounded explanation with exact caller and optional receiver source, conditions for local responses, the declared handoff, and an explicit stop at uncaptured storage, transport or consumer behavior. An engineer can review the claims; a process owner can see which business outcome still needs confirmation.

Computation thread, CLI thread and documentation process

Computation thread — the concept
The bounded path relevant to your question. It can involve one function, several functions or a declared service handoff.
Managed CLI thread — a local analysis container
A versioned object binding 2–8 existing sessions and their service/member aliases. It supports qualified read-only multi-session analyses. Its membership is not proof of a cross-service call or an operating-system thread.
Documentation process and process.thread — a saved explanation
A process records an intended scope, trigger, participants and outcomes. Its optional source-bound thread presents selected complete methods and declared steps. Authors and reviewers supply meaning; the renderer checks bindings and keeps uncertainty visible.

None of these is an operating-system execution thread, distributed tracing span or guarantee of a complete program slice.

Who decides what?

  • Engineer: supplies authorized repositories, revisions, build inputs and the engineering question; chooses checks and whether to apply or publish a result.
  • Agent or documentation author: selects relevant evidence, writes an explanation and makes proposed relationships and unknowns explicit.
  • Codeclew: captures supported facts, enforces bounds and bindings, and manages supported preparation, validation and publication operations.
  • Reviewer: checks whether an interpretation follows from the selected evidence and whether its scope is useful. Model agreement is not production observation.
  • Domain owner: confirms intended business rules and outcomes when source alone cannot explain the intent.

Session, profile, compilation and Check

Session
A managed analysis record that binds work to a repository revision, language, selected compilations and runtime. Use its returned identity to continue supported analysis; it is not a running application session.
Profile
A named capability contract selecting an analysis path, required tools, admitted operations and limits. Two profiles for the same language can offer different authority or change support.
Compilation
The build-selected unit of code and compiler inputs, such as a module's main source set or a Cargo target. It is not the entire monorepo or an instruction to compile arbitrary code. Documentation SOURCE scopes instead select explicit source paths without invoking a compiler.
Check
A saved documentation evidence snapshot containing selected service evidence, revisions, dependencies and unresolved gaps. Its returned handle lets later reads use the same evidence. A Check is not a verdict that the application is correct or its documentation complete.

Start with one question

Have a local checkout and a branch or tag identifying the revision you intend to analyze. For compiler-backed work, make the project's required toolchain and restored dependencies available. Then run the repository doctor to discover candidate scopes:

clew doctor repository --repo "$PWD"

Give your agent the question and starting point, then ask it to choose a relevant ready scope from that report and return exact evidence plus remaining gaps. Use the editable question/root template if needed. The doctor is discovery, not an analysis answer. For native documentation from saved evidence, start with the saved Check and process/declaration selection instead; a managed session container is not a prerequisite for every documentation page.

Use the installation steps and the pinned agent workflow below for complete commands. Codeclew runs locally; your agent uses its configured model/provider. Optional model-assisted authoring is a separate choice, not a required hosted Codeclew service.
