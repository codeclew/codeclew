Languages, annotations and evidence

Support belongs to a workflow and a captured toolchain, not just a language name. Start with the question and check which evidence that workflow can return.

Which kind of work is supported?

These are the 0.13.34 release contours, not a promise that all languages share all features. SOURCE means bounded syntax evidence without a project compiler; compiler-backed means facts from the admitted compiler/project inputs. A framework interpretation and authored documentation remain separate layers.

What an annotation tells Codeclew

Annotations and attributes can help locate entrypoints such as request handlers or scheduled work. There are two input paths with different authority. Shared framework rules do not make their evidence equivalent.

Compiler-backed path: the admitted language compiler supplies portable facts such as resolved annotation/attribute types, arguments, available defaults and supported inheritance relationships. A framework module interprets those facts under a named policy. The result retains both compiler provenance and the framework derivation.

For example, a Spring mapping annotation can support a derived HTTP-entrypoint declaration, and an admitted ASP.NET Core MVC route attribute can support a controller/action route. This answers “what does this source declare?” Deployment configuration and runtime registration remain separate evidence.

Composed annotations, inherited methods, unresolved defaults and unavailable metadata need their own coverage checks. A short annotation name or nearby string is not an interchangeable substitute for a resolved type. Custom frameworks do not become supported merely because their annotations resemble Spring or MVC.

SOURCE annotations: useful declarations without compiler resolution

SOURCE path: Java and Kotlin syntax capture can supply annotation evidence even without the project compiler or framework libraries. Fully qualified spelling or a matching explicit import qualifies a name for the supported rules; Kotlin explicit import aliases are supported too. The shared Rust Spring rules can then derive source-declared entrypoints while preserving the separate SOURCE / SYNTAX authority. This does not make the name compiler-resolved.

Declaration example from the pinned Spring qualification fixture. It illustrates the SOURCE result, not an observed deployment.

import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.PostMapping;
@RestController
@RequestMapping("/orders")
public class Orders {
    @PostMapping(path = "/reserve")
    public int reserve(int quantity) { return quantity; }
}

Result: a source-derived declaration of POST /orders/reserve, combining the class and method paths. An engineer can use it to locate a candidate handler and document its declared route. The Kotlin fixture obtains the same declaration through an explicit PostMapping as Reserve import. Neither result proves controller activation, request execution or runtime registration.

Wildcard or ambiguous imports and locally shadowed annotation names remain unresolved. Arbitrary source-defined composed annotations and member defaults remain gaps; their behavior is not recovered from a short name. Unresolved constants and runtime expressions stay unknown rather than being evaluated. Available built-in framework rules still have their own declared limits.

Choose this path when a source declaration is enough to make progress. If the question needs compiler resolution, inherited types or metadata that SOURCE does not establish, obtain an admitted compiler capture or retain that specific missing evidence. See the pinned Java/Kotlin qualification and its exact limits and the maintained SOURCE workflow.

Four layers to keep distinct

  1. Retained source / syntax: exact code and bounded lexical structure at a recorded revision.
  2. Compiler facts: admitted declarations, types, calls or local control flow within the selected compiler scope.
  3. Framework-derived facts: a named module's interpretation of those facts, with its own policy, coverage and boundaries.
  4. Declarations and authored meaning: intended process scope, a proposed service relationship or a reviewed explanation. Source bindings make these inspectable; they do not turn prose into compiler or runtime evidence.

Runtime observations, when explicitly collected and attached, are another scoped source of evidence. Static annotations alone do not replace them.

What “managed change support” means

A mutation-capable profile admits only the supported edit plans and validation rules for that selected contour. Preparation creates an isolated candidate, validation evaluates it, and explicit publication applies an eligible result. An analysis session, multi-session thread or readable source packet does not authorize a write.

Before relying on a change, inspect the admitted operation and its validation result. Kotlin compiler diagnostics, or Python/Rust syntax checks, have different authority. None alone proves business correctness, deployed behavior or safety of arbitrary repository-wide edits.

The pinned change workflow and language-mutation pilot below define the current exact plan constraints. Use them for execution rather than extrapolating from a “mutation” boolean.
