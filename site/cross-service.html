Build a cross-service thread

Connect independently scoped evidence through explicit handoffs. A useful cross-service account explains both sides of a boundary and preserves what the connection does not establish.

Start with a question and the participating source

Choose a caller entrypoint and the business or engineering outcome to investigate. Capture each relevant service at an explicit revision using its supported workflow. Keep the service, compilation and exact callable identity attached to every fragment; two repositories do not need to share a revision or language.

To continue into a receiver, provide that receiver's captured evidence and an explicit relationship to the caller. A managed CLI thread can bind existing sessions for qualified multi-session analysis. A maintained documentation process can instead compose saved service evidence and declared interactions. Neither container discovers a live distributed execution by membership alone.

Make the handoff a first-class question

Part of the accountWhat to recordWhat remains separate
CallerInput handling, selected branches, outgoing operation and local success/error paths, with exact source.Whether the request reached any service.
Transport and contractDeclared method/path or topic, request and response/payload shapes, timeout/error behavior, and which side each claim comes from.Wire compatibility, effective configuration, broker subscriptions and runtime delivery.
RelationshipManual declaration, agent proposal or a specific admitted derivation, with independent authority and unresolved checks.A compiler-resolved local call is not automatically an HTTP/Kafka receiver mapping.
Optional receiverThe exact captured receiving method and its own decisions, effects and result, plus a link back to the calling process.Uncaptured implementation details, commit, consumer execution and end-user completion.

A manual relationship can be valuable: it states what an engineer wants investigated. An inferred relationship can suggest a candidate. Keep both inspectable and labelled; similar names, DTO types or topic strings alone do not prove service identity, ownership or delivery.

Checkout → reservation → event

Illustrative example — the fictional services introduced in the overview. The arrows below denote a declared reading path, not observed execution order.

  1. Checkout handler: explain the validation and the reservation request. Distinguish its public route from the outgoing inventory path. Read its timeout and error paths before promising what a failed response means.
  2. Declared inventory handoff: record the proposed target and the contract facts available from each service. Link the receiving handler if it is captured. If it is missing, stop the call expansion there and name the missing receiver evidence; keep the caller explanation useful.
  3. Inventory handler and storage: explain the selected implementation, if available. An awaited save is a source call. To describe transaction or conflict behavior, inspect the repository implementation separately. A staged event is a delivery record, not proof of broker publication.
  4. Publisher and consumer views: link them as separate accounts with their own capture, freshness, interpretation and gaps. A publisher's source order does not establish when another service consumed a message. A local accepted response or outbox row is not the customer-visible outcome.

In this example, a timeout can leave reservation completion unknown. Determining retry safety needs additional evidence about the actual transaction, identifiers, duplicate handling and delivery behavior; the timeout wrapper alone cannot settle it.

Explain failure at the right boundary

Separate invalid input, a caller-side exception, a receiver rejection and an unknown completion outcome. State which component returns the error and which effects may remain unresolved. A caught request or response-parsing error does not, by itself, demonstrate rollback at the receiving service.

For asynchronous work, distinguish source-level send/acknowledgment calls from delivery, consumption and business completion. Retry policy and duplicate handling need their own evidence. Neither a diagram arrow nor an outbox label grants exactly-once behavior.

When evidence or a linked explanation changes

Recheck the selected source and dependency scope through the supported lifecycle. A changed receiver or child explanation can leave an earlier composition stale or requiring a new selection. Keep the retained version available for comparison; do not silently splice newly authored text into an older accepted process.

For an interaction-only change, docs recompose can reuse the retained source capture. Previously accepted operations keep their earlier bindings and addresses, marked changed where needed, until updated content is accepted. A new declaration does not silently rewrite an old explanation.

A source digest verifies a binding, not the truth of an explanation. Review changed interpretations separately. A missing or stale child is a useful visible boundary, not permission to fill in the rest of the process.

Choose an execution recipe

For source exploration, use the installed agent workflow and exact returned references. For maintained process documentation, use the saved process and boundary-contract recipes below. Begin with one useful bounded account, then add receiver or continuation evidence where the question actually needs it.

The Weather documentation reader is a real public example with its own retained evidence and limitations. It is separate from the fictional checkout example and is not proof of a production runtime trace.
